## 一、选型的第一原则：先定部署约束，再选技术（反过来必返工）

本项目的每个「非主流」选择都是从部署目标倒推的，你的新项目应该先回答这四个问题：

| 问题                 | 本项目的答案                   | 推导出的选型                                              |
| -------------------- | ------------------------------ | --------------------------------------------------------- |
| 部署在什么硬件上？   | 客户现场的 **ARM 低配盒子**    | 无构建前端、程序化几何优先、三级画质自适应                |
| 有外网吗？           | **内网/离线**                  | 三方库全部本地化（不碰 CDN）、镜像走国内源                |
| 谁维护、多久看一次？ | 交付后**无人运维**             | SQLite（拷目录即迁移）、compose `restart: unless-stopped` |
| 数据量级多大？       | 100 台 @20Hz = **1.7 亿行/天** | 单机 SQLite 撑不住 → 必须设计热窗+降采样                  |

## 二、分层选型要点

**前端**

- **构建 vs 无构建**：无构建（原生 ES Module）的真实收益是「改完刷新即生效 + 离线可用 + ARM 低配机直跑」，代价是没有类型检查和打包优化。如果团队大、需要 TS，可以上构建，但**三方库仍要本地化进仓库**——离线部署时任何 CDN 都是单点；
- **懒加载是纪律不是优化**：9 个格式加载器 520KB、IFC 7MB、pdf.js 1.7MB——全部动态 `import()`，首屏指标定死；
- 渲染库选 Three.js 这类纯前端方案没毛病，但**画质分档机制（设备检测定档 + 帧率升降档）要在架构期就设计进去**，后补很痛。

**后端**

- 轻量框架（Flask 这类）够用，但**开发服务器绝不能上生产**——Flask dev server 单线程，要换 gunicorn/uwsgi，这是本项目上线清单第一条；
- WS 和 REST 在同一进程还是分开？本项目同进程（端口不同），简单但共享 GIL——规模上去再拆；
- Python 选型时注意依赖的 **ARM wheel 可用性**：本项目全选纯 Python 依赖（flask/websockets/paho-mqtt/amqtt）就是为了 ARM 上零编译；一旦引入 numpy/opencv 这类 C 扩展，arm64 构建复杂度立刻上一个台阶。

**存储**

- SQLite 的适用边界：单机、写入 ~5000 条/秒以内、无人运维——本项目实测平台侧 5000+/s p50 32ms 没问题，但**磁盘是线性增长**的（本机已积 2GB）；
- 接口抽象（`TimeSeriesStore`）必须第一天就有——这是「先 SQLite 后换 TDengine」这条路成立的前提；
- retention 策略要限**条数**不只是天数（单设备能占 84% 的坑）。

**消息层**

- 内嵌 Broker 只能当演示件（amqtt 实测 ~800 条/秒饱和，且长跑会静默挂死——三天前刚发生过）；
- 生产选 EMQX 或 Mosquitto，compose 里 healthcheck + 平台侧「Broker 不可达时其余功能照常启动」的降级；
- 主题约定收敛成一份代码文件，平台和设备共用。

## 三、部署环境的限制清单（每条都是实测踩到的）

| 限制             | 具体表现                                                     | 对策                                                         |
| ---------------- | ------------------------------------------------------------ | ------------------------------------------------------------ |
| **网络**         | Docker Hub 被 DNS 污染；内网无外网                           | 镜像经国内 mirror 拉取后重打 tag；**不要改 /etc/docker/daemon.json**（会破坏现场其他服务） |
| **端口**         | 现场端口被占是常态（本项目 8000 被机器人服务占用且不可杀）   | 所有端口走环境变量（HTTP/WS/MQTT 都要），部署文档写清「先探测再选端口」 |
| **HTTPS**        | 现场往往没有证书和域名                                       | 不上 TLS 就等于口令明文（本项目鉴权整套因此形同虚设）——要么自签证书进交付包，要么明确接受内网明文的风险签字 |
| **进程管理**     | nohup 起的进程**重启即丢**（本项目 8100 就是这样，机器重启就没了） | systemd unit 或 compose restart 策略；杜绝手工 nohup         |
| **双进程劈叉**   | 同端口起两个进程：REST 在新的、WS 在旧的，只有实时类断言失败 | 启动脚本里先查端口再启动；健康检查看**计数器增量**而非存活   |
| **arm64 未验证** | buildx 多架构构建，arm64 分支没在真机跑过                    | **交付前必须在目标机型实测**，CI 交叉构建通过 ≠ 能跑         |
| **磁盘**         | 时序数据无限增长                                             | retention + 降采样进交付默认配置，别留给客户配               |
| **时钟**         | 时序数据和回放依赖 ts                                        | 现场必须 NTP，交付清单写明                                   |
| **客户端浏览器** | 低配盒子上的浏览器 WebGL 能力弱                              | 画质自适应 + 明确最低浏览器要求；无头测试环境的 SwiftShader 只有 4~9fps，帧率数字不代表真实硬件 |

## 四、上线前检查清单（直接可抄）

1. gunicorn 替换 dev server + TLS 终端；
2. 外部 EMQX（关 `TWIN_MQTT_EMBEDDED`）+ EMQX 匿名改账号密码；
3. 管理员初始密码显式设置（否则随机生成打印在日志里）；
4. 图纸/模型若敏感，静态文件另行保护（SPA 惯例是不鉴权，要明确这是取舍）；
5. 数据 volume 挂载 + 备份策略（本项目迁移 = 拷 `data/` 四个 SQLite）；
6. 目标机型（含 arm64）实测一遍 compose 全链路。

最后一条建议沿用上次结论：**`shared/` 契约 + 主题约定 + REST/WS 信封这三样冻结为跨系统协议**，选型怎么换都不影响互通。这份内容要不要我也补进 [重建同类平台要点.md](vscode-webview://1c5kcdj7umu8t4stmt793a8k8l7aq6h3pfhh5kkj8vap14ici81d/docs/guides/重建同类平台要点.md)？现在文档里只有架构复刻部分，选型和部署约束这两节加上才完整。
